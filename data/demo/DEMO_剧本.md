## 演示流程（5 分钟）

### 第一幕 — 候选人 A 张明远（2.5 分钟）

1. 上传 JD + 张明远简历 → 点击开始
2. 等待解析 + 出题（流式展示）→ 指着能力缺口分析讲解
3. 按下方预设回答逐轮演示：

#### 第 1 轮 — 问 LangChain/Agent 基础

回答（好→应该触发 deepen）：
> 我在腾讯实习的时候用过 LangChain，主要是用它的 Chain 和 Agent 模块搭建了一个内部知识库的问答系统。具体来说是用 ConversationalRetrievalChain 把检索到的文档和用户对话历史一起传给 LLM，然后 Agent 部分用 OpenAI Functions 做了工具调用，比如搜索内部文档、查询数据库。遇到的一个问题是 token 消耗比较大，后来用 summary memory 替代了 buffer memory 解决了。

#### 第 2 轮 — 追问 deepen

回答（模糊→触发 clarify）：
> 嗯...性能优化方面，我感觉主要就是减少 token 消耗吧，还有就是用了缓存。具体的话，就是把一些常用的问答结果缓存起来，这样就不用每次都调 LLM 了。

#### 第 3 轮 — 追问 clarify

回答（跳过→触发 switch）：
> 跳过

#### 第 4 轮 — 切换到新技能

回答（模糊→触发 clarify）：
> ChromaDB 我用过，就是存文档向量然后做相似度检索。配置的话就是设一下 persist_directory，然后 collection 的名字。检索的时候用 query 方法传文本进去就行。

4. 点击「结束面试」→ 展示报告 → **指着 5 维度评分说"注意分数"**

---

### 第二幕 — 切换候选人 B（2.5 分钟）

1. 点击「再来一场面试」→ 上传同一个 JD + 候选人 B 简历 → 点击开始
2. 按预设回答演示：

#### 第 1 轮 — 问 Agent 框架

回答（好→触发 deepen）：
> 我主要用 LangGraph 做过多 Agent 协作。具体场景是把 JD 解析、简历分析、面试出题、答案评判拆成四个独立的 Agent，用 LangGraph 的 StateGraph 做编排。JD 解析和简历分析可以并行跑，然后 match skills 是纯逻辑不做 LLM 调用节省成本。多轮追问的部分用条件边实现，根据上一轮评判结果决定是 deepen、clarify 还是 switch 到下一个技能。整个状态用 TypedDict 管理，rounds 用 operator.add 自动累积。

#### 第 2 轮 — 追问 deepen（答得好）

回答：
> 编排这块遇到的最大的坑是循环图的终止条件设计。一开始我只设了轮次上限，结果发现 LLM 有时候会反复追问同一个问题，或者候选人连续跳过三次还在继续问。后来加了三个终止条件：连续空回答检测、技能覆盖度检查、以及 LLM 评判结果里的 next_action 字段。还有一个有意思的点是条件路由——LangGraph 的 conditional_edges 可以根据状态字段动态决定下一个节点，我把 terminate 检查逻辑放在一个独立的 decide_next 节点里，这样图的逻辑就清晰很多。

#### 第 3 轮 — 追问 deepen（继续深挖）

回答：
> 对，MCP 协议这块我也实践过。我把 JD 解析、简历解析、题库管理分别封装成三个独立的 MCP Server，每个 Server 注册自己的 tool。然后用 FastAPI 做了一个 Gateway 统一入口，ServerRegistry 维护 tool_name 到 server 的映射，请求来了按工具名自动路由。还有一个熔断保护——每个 Server 配一个 CircuitBreaker，连续失败 3 次就自动熔断，30 秒冷却后放一个探测请求，成功了就恢复，失败了继续熔断。限流用的是令牌桶算法。

4. 点击「结束面试」→ 展示报告 → **两组报告对比，分数明显不同**

## 总结话术

> "同一个 JD，两个候选人——第一个人履历漂亮但问答浅，系统通过追问策略把差距测出来了。第二个人实战经验丰富，追问越深回答越具体。最后两边的评分报告、维度得分、录用建议都拉开了明显差距。这说明这套系统不是在填问卷，是真的能区分候选人水平。"

## 备用：如果 API 抽风

- 不要慌，说"API 调用需要一点时间"
- 如果超时失败，系统会自动重试（正好展示指数退避重试机制）
- 如果连续失败触发熔断，健康检查端点能看到 breaker 状态
