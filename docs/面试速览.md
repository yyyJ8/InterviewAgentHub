## 一、60 秒项目介绍（背下来直接用）

> "InterviewAgentHub 是一个多 Agent 的面试系统：上传 JD 和简历，系统解析出技能缺口，然后按缺口逐轮追问面试，最后出五维度评分报告。
>
> 技术上我做了两件比较关键的事。
>
> **第一是把 MCP 协议真正落地**：项目里有 3 个独立的 FastMCP Server（JD 解析、简历解析、题库），我用 FastMCP 原生的 Streamable HTTP transport 把它们聚合成一个标准 MCP 端点，6 个工具。经官方 MCP 客户端 SDK 验证，Claude Desktop、Cursor 这类客户端可以直接连过来调用 —— 是协议合规的服务端，不是内部调用约定。
>
> **第二是编排的选型**：我一开始用 LangGraph 的 StateGraph 编排整条链路，阶段一是批处理模式，跑得通。改成多轮交互后我实测发现它的执行模型不匹配 —— 单次 `resume` 会让图继续按边流转（我一次推进了 3 轮），设两个挂起点时 resume 值又无法区分目标。所以我保留了它的状态类型和节点函数式设计，把调度和持久化改为自研。
>
> 工程上是 5500 行生产代码 + 85 个测试全绿。"

**如果只有 30 秒**，只讲"标准 MCP 服务端（6 工具、官方客户端验证）+ 85 个测试"这两句。

## 二、必被追问的问题与标准答案

### Q1. 为什么不用 LangGraph，自己写编排？

**这是最可能被问、也最能加分的问题。**

> 阶段一我用了 LangGraph 的 `StateGraph`：6 个节点串成图，`run_interview` 一次传入全部答案，`async for event in interview_graph.astream(...)` 从头跑到尾。那是批处理模式，图的执行模型完全适配。
>
> 阶段二改成多轮交互后就不匹配了。我用 `interrupt`/`resume` 试过，实测有两个问题：
> 1. 单次 `Command(resume=...)` 后，图会**继续按边流转**直到下一个中断点或 END —— 我实测一次 resume 直接推进了 3 轮
> 2. 在"出新题"和"等答案"各设一个挂起点时，传入的 resume 值**被错误的挂起点消费**，轮次计数恒为 0
>
> 另外 `MemorySaver` 是进程内存储，而我的会话要跨 Gateway 重启存活。
>
> 所以我保留了 LangGraph 的 `TypedDict` 状态定义和节点函数式约定（`async def xxx_node(state) -> dict`），去掉图的调度与检查点，改为按请求逐轮直接调用节点函数。

**⚠️ 必须补一句（否则会被反驳）**：
> "需要说明的是，LangGraph 提供 SQLite / Postgres 类型的 checkpointer，所以跨进程持久化是可配置的，**不是它做不到**。真正的问题是中断语义不匹配 —— 要做到'一次请求恰好一轮'得逆着它的设计去调，改造代价高于收益。"

**如果追问"代价是什么"（一定要主动承认）**：
> 代价我清楚：流程不再一眼可见（完整链路散在 `init_interview`、`judge_and_decide`、`generate_next_question_stream` 三处）；路由规则分散在 `_next_action_label`；**状态合并全部手写，容易出错** —— 我确实踩过一个 bug：技能索引被两个节点各 +1 导致一次切换跳两个技能。如果将来要做"多候选人批量面试"或"执行历史回放"，图的优势就能发挥，我会把它接回来。

**加分点**：这个决策我写进了技术手册的「9.0 架构演进」，包含实测数据和已知代价。

### Q2. 你的 MCP 是"协议"还是"自己封的函数"？怎么证明？

> 是标准协议。项目里 3 个 FastMCP Server 各自用 `@mcp.tool()` 定义工具，我用 `streamable_http_app()` 拿到 FastMCP 原生的 Starlette 应用，挂到 Gateway 的 `/mcp` 路径上暴露。
>
> 证明方式是协议层验证：官方 MCP Python 客户端 SDK（`streamablehttp_client` + `ClientSession`）连真实运行的 uvicorn 服务，完成 `initialize` 握手、`tools/list` 拿到 6 个工具及完整 `inputSchema`、`tools/call` 成功执行。协议版本协商到了 `2025-11-25`。
>
> 另外项目里还保留了一个 `/mcp/{tool_name}` 的运行时直调端点，那个是**私有约定、不是 MCP 协议** —— 我在文档里明确标注了区别，避免混淆。

**追问"聚合是怎么做的"**：
> 建一个聚合的 FastMCP 实例，遍历三个 Server 的 `_tool_manager._tools`，用 `add_tool()` 把工具函数连同 `name`/`description` 注册进去。`inputSchema` 是 FastMCP 从函数签名自动生成的，不需要手写。

**追问"踩过什么坑"（真实且具体，很加分）**：
> 四个坑都实测出来的：
> 1. Starlette 的 `Mount` **不会执行子应用的 lifespan**，而 FastMCP 的 session manager 必须在 lifespan 里启动 → 报 `Task group is not initialized`，要由外层应用显式 `async with session_manager.run()`
> 2. `TransportSecuritySettings.allowed_hosts` **默认是空列表 = 拒绝所有 Host**（返回 421），而且**不支持 `"*"` 通配**，只支持精确值或 `"host:*"`
> 3. 挂载前缀会与内部路径拼接：`mount("/mcp")` + 内部 `/mcp` → 实际端点变成 `/mcp/mcp`。所以要把内部路径设为 `/`，对外才是 `/mcp/`
> 4. `session_manager.run()` **每个实例只能调用一次**，重复进入会抛错 —— 这影响了我的测试设计（要共享实例）

### Q3. 85 个测试测的是什么？cover 到什么程度？

> 分四类：
> - **`test_question_bank.py`（15 项）**：题库沉淀的质量门槛、去重（归一化后比对）、外部写入不被覆盖
> - **`test_seed_read_path.py`（16 项）**：技能匹配取题、出题提示双来源、**题库文件损坏时拒绝写入**（避免覆盖丢数据）
> - **`test_mcp_protocol.py`（7 项）**：MCP 握手、`tools/list`、`tools/call`、缺少 session id 被拒
> - **`test_gateway_integration.py`（5 项）**：dev/prod 鉴权差异、lifespan 工具注册、空答案 400、未知会话 404
> - 另有 **`test_regression_fixes.py`（10 项）**：每个修过的 bug 配一个回归测试
>
> **我最看重的是回归测试那一类**：每个修过的 bug 都留一个测试锁住，防止再犯。比如"技能索引双增"那个 bug，测试直接断言一次 switch 只能前进一个技能。

**平均每个 bug 都有对应的测试**，这是我认为比覆盖率百分比更有意义的做法。

### Q4. 题库这条链路解决什么问题？

> 原来题库是"只写不读"的：有个 `add_to_seed_bank` 工具，但**全项目零处调用**，面试出的题只进向量库，从不回流题库，所以题库永远是初始那几道。
>
> 我做了两件事：
> 1. **闭合写入**：面试结束时自动把本场出过的题沉淀进 `seed_questions.json`，带质量门槛（题干 ≥15 字符、作答要点 ≥2 条且每条 ≥5 字符）和归一化去重
> 2. **闭合读取**：出题时**同时检索两个来源** —— 向量库（过往已出的题，语义检索）+ 种子题库（按技能匹配，附带作答要点作为考察角度参考）
>
> 实测：题库从 12 道涨到 14 道（把向量库里的历史积累导入），再跑一次是 0 新增 / 2 跳过重复，幂等成立。

**追问"分层是什么"**：
> `seed_questions.json` 是题库的**唯一真相来源**；向量库 `ih_question_bank` 只是"已出题目"的**检索索引**，用于避免重复出题。两者职责不同，我在文档里也这么区分。

**追问"坑"（这个坑很值钱）**：
> 有个坑：题库文件如果 JSON 损坏，`_load_seed` 会抛异常。如果简单改成"返回空列表"，沉淀时就会把整个题库**覆盖成只剩本次新增的题** —— 数据全丢。所以我加了 `SeedBankCorruptedError`，明确区分"文件不存在（返回空）"和"文件损坏（抛错）"，沉淀路径捕获后**直接中止且不写入**。有测试专门验证损坏文件在沉淀后内容原样保留。

### Q5. Embedding 用的什么？为什么？

> `BAAI/bge-m3`，1024 维，走 SiliconFlow 的 OpenAI 兼容 embeddings 接口，这个模型在平台上免费。
>
> **模型 id 必须写全 `BAAI/bge-m3`，写成 `bge-m3` 会返回 400。**

**追问"维度变了怎么办"（这是真实处理过的问题）**：
> 项目早期用的是本地 `bge-base-zh-v1.5`（768 维），换到 bge-m3（1024 维）时维度不兼容 —— ChromaDB 的集合维度建库时就锁死了。我在写入和检索路径都做了维度冲突检测，遇到就重建 Collection 并记录 warning。迁移时我把旧的 2 条向量从备份里取出重新嵌入写回，数据没丢。

**追问"本地模型"**：
> 本地模型降级为兜底，而且是**惰性加载**：早先的实现会在初始化时就构造本地 SentenceTransformer，实测白付约 **30 秒**启动开销，即使 API 全程正常。改成 `_LazyEmbedder` 后只在 API 首次瞬时失败时才加载。实测初始化从 30 秒降到 **0.97 秒**，而模拟 503 时本地模型仍能正确按需加载（768 维）、且不重复加载。

**追问"输入长度会不会超限"（这题我给过错误建议，正确答案是"不会"）**：
> 不会。Embedding 只用于题目文本和技能名这类短文本；JD 和简历在解析前已经截断到 3000 字符，所以不会触及 bge-m3 的 8192 token 上限。

### Q6. 熔断和限流怎么实现的？

**限流**（`RateLimiter`）：
> 令牌桶，按时间比例惰性补充：`refill = int(elapsed / window * max)`，上限是 `max`。默认 60 次/分钟，按 IP 维度。桶数量超过 1000 时触发一次清理，移除超过 2 个窗口未活动的条目。

**熔断**（`CircuitBreaker`）：
> 三态模型，**按 Server 粒度**（jd-server / resume-server / question-bank-server 各一个）。连续失败 3 次打开，30 秒冷却；冷却期过后 `is_open` 会把失败计数清零，允许一次试探调用，成功就恢复。

**如果追问"多 worker 怎么办"（诚实答）**：
> 现在限流桶和熔断器都是**进程内**状态。单实例部署够用，但多 worker 下需要换成 Redis 做共享状态，而且熔断应该做到**工具粒度**而不是 Server 粒度。这块是目前的设计边界，我清楚。

### Q7. 重试策略是什么？

> 两层，都在 Agent 基类里：
> - **LLM 返回空内容**（通常是服务端瞬时过载）→ 退避 **1s → 3s → 9s**（`backoff_base * 3^attempt`）
> - **JSON 解析失败** → 退避 `backoff_base * 2^attempt`
>
> `max_retries=2`，即最多 3 次尝试。另外解析场景用 `temperature=0.3` 提高输出稳定性。

**追问"为什么两种退避基数不同"**：
> 空响应是服务端过载，需要更长的等待；解析失败往往是模型输出格式抖动，重试通常很快就能拿到合规输出，所以退避更短。

### Q8. Prompt 变量校验是怎么做的？

> 加载模板时用正则 `\{(\w+)\}` 提取全部占位符存进 `PromptTemplate._variables`；`format()` 时比对传入参数：
> - **缺失** → 抛 `KeyError` 并**列出具体缺哪些变量**（对比直接用 `str.format()` 只会给一个笼统的 KeyError）
> - **多余** → 记 warning 并忽略
>
> 另外 `PromptTemplate` 实现了 `__str__`/`__len__`/`__contains__`，所以既能传给不需要变量校验的 Agent 当普通字符串用，也能直接做长度和包含判断。

### Q9. 4 个 Agent 各自做什么？为什么反馈 Agent 不在图里？

> - **JDParserAgent**：JD 原文 → 结构化 `JD`（技能及权重、加分项、经验要求）
> - **ResumeAnalyzerAgent**：简历原文 → 结构化 `Resume`（技能熟练度、项目经历）
> - **InterviewerAgent**：出题（4 类：首题 / deepen / clarify / switch）+ 评判回答
> - **FeedbackAgent**：汇总轮次 → 五维度评分报告
>
> 反馈 Agent 是**面试终止时由 Gateway 直接调用**的，不在逐轮循环里 —— 因为它只在最后跑一次，放进循环没有意义。

**追问"追问策略的驱动力是什么"**：
> `JudgeResult.next_action` 是唯一动力源，四个值：`deepen`（答得好，深挖）/ `clarify`（答得模糊，要求澄清）/ `switch`（答不上，换技能）/ `end`。终止还有三个兜底条件：连续空回答达到 3 次、轮次达到上限 10、技能全部覆盖。

### Q10. 技能排序的规则是什么？

> `_sort_key` 是升序元组：`(是否工具技能, 是否加分项, 是否缺口, 是否有项目经验, -权重)`。
>
> 直觉是：**工具技能永远垫底**（Docker/Git/IDEA 这类，用 `_TOOL_KEYWORDS` 黑名单判定）→ 加分项次之 → 然后是缺口 → 有技能无项目 → 有项目经验的优先。同档内按权重降序。
>
> 这解决了一个真实问题：JD 里 Docker 和 LangGraph 都算技能，但按出现位置加权时 Docker 可能排前面，导致面试第一个问题问 Docker 而不是核心技能。

**⚠️ 如果被问"这里用了语义匹配吗"——如实答否**：
> 没有。`matcher.py` 是**纯规则字符串匹配**（技能名小写精确匹配 + 工具关键词降权）。语义匹配在优化路线图里规划过，但没有实现 —— 我文档里明确写了当前是纯字符串匹配。
>
> **（这条千万别含糊，面试官打开 `matcher.py` 就能看到只有字符串处理。）**

### Q11. 会话状态怎么持久化？

> 有两个状态载体，职责不同：
> - **编排层**用 `TypedDict` 的 `InterviewState`（图/节点之间传递）
> - **持久化层**用 Pydantic 的 `InterviewState`，通过 `SessionStore` 写成 `data/sessions/{id}.json`
>
> 两者用 `_state_to_pydantic()` / `_pydantic_to_state()` 互转。**每轮 `judge` 都落盘** —— 这里修过一个 bug：原先只在面试终止时才保存，导致中间的技能进度和空回答计数每轮都丢，表现是"每轮都从第一个技能重开"。

**追问"为什么不用数据库"**：
> 规模决定的：一场面试一个文件，几十 KB。JSON 便于直接看和调试，也便于用 CLI 的 `history` 命令直接读。等要支持多用户并发编辑或题库上千道题时再考虑 SQLite，现在做是过度设计。

### Q12. 项目里有过哪些比较严重的 bug？（如实答，这题很能体现深度）

挑三个讲，每个都带根因：

1. **技能索引双增**：`generate_question_node` 的 switch 分支和 `decide_next_node` **各自把技能索引 +1**，导致一次切换跳两个技能。根因是"索引推进"这个职责没有唯一归属。修法是**只让 `decide_next_node` 推进索引**，出题侧只读不写。已加回归测试。

2. **技能进度每轮丢失**：`current_skill_index` 不在 Pydantic 的 `InterviewState` 里，Gateway 每轮重建状态时硬编码成 0。表现是"重复出同一道题"。修法是补字段 + 每轮落盘。

3. **题库损坏会覆盖丢数据**：见 Q4。修法是引入 `SeedBankCorruptedError`，让破坏性写入路径在读到损坏文件时中止。

**共同点**：都是"看起来对、实际不生效" —— 声明了但没生效，或者职责没有唯一归属。所以我现在倾向于"每个 bug 配一个回归测试"。

## 三、主动暴露的短板（抢在面试官发现前说）

**为什么主动说**：面试官自己发现 = 你藏了；你主动说 = 你有判断力。以下三条都真实存在。

### 短板 1：`gateway.py` 太大（808 行，7 个职责）

> "这个文件现在 808 行，混了 7 类职责：日志过滤器、鉴权、限流、熔断、Server 注册中心、状态转换、8 个路由端点，外加应用装配。**我知道应该拆** —— 至少拆成 auth / rate_limit / circuit_breaker / routes / state_codec 五块，其中状态转换那部分（约 130 行、5 个函数）不依赖 FastAPI，更适合独立成模块。目前没拆是优先做了协议和正确性方面的修复。"

### 短板 2：没有部署，无法在线体验

> "目前只在本地跑通，没有 Dockerfile，也没有公开部署。**要展示给别人只能自己 clone 跑** —— 这是我下一步最该补的，因为它直接影响别人能不能快速验证。"

### 短板 3：RAG 比较薄

> "向量库目前只用于'避免重复出题'这一个场景，种子题库只有十几道题。**没有做混合检索、没有 Reranker、没有大规模语料**。我在另一个项目里做过 ChromaDB 语义 + BM25 + RRF 融合 + LLM 重排的完整链路，但这个项目里 RAG 不是重点。"

### 可以顺带提的（较小）

- 限流/熔断是进程内状态，多 worker 需换 Redis
- `interview_talk` 端点已标记弃用但保留（有降级路径依赖）
- 熔断按 Server 粒度，理想是按工具粒度
